# 設定バックアップ・ZIP更新・復旧

## データの持続

テーマ設定は `shikipress_settings`、カテゴリー対応はその中のterm ID、分類/スラッグ/SEOの個別情報は `_shiki_*` 投稿メタ、カテゴリーはWordPress標準taxonomyへ保存します。無効化・再有効化で記事・設定・カテゴリー・URLを削除/初期化しません。テーマ独自の定期ジョブは無効化時に解除し、再有効化で重複登録しません。

別テーマへ変更すると、四季デザイン、下部タブ、分類/スラッグ候補、広告、テーマSEO、HTMLサイトマップshortcode、独自メタの表示、集計や検査が停止します。WordPressの投稿/カテゴリー/保存済みスラッグは残ります。再利用する場合は `get_option('shikipress_settings')` と標準メタAPIから必要な設定/メタを新テーマへ移行してください。独自shortcode `[shiki_sitemap]`、広告ブロック等は移行先で置き換えます。

## 設定JSON

ShikiPress→設定バックアップからエクスポート。APIキー・パスワード等は含めません（翻訳キーはwp-config.phpの定数のみ）。実行可能広告/CMPタグは通常バックアップから分離。別途のコード移行は権限と明示選択が必要です。

インポートは形式検証→変更内容のプレビュー→適用する領域の選択→適用の順です。適用直前の設定を保持し復元できます。インポート/復元後、広告と外部コードはテスト/未承認へ戻します。外部通信は勝手に再開しません。別環境のpage/term IDは対応先が異なるため目視確認してください。

JSONはテーマ設定のみです。記事、画像、ユーザー、WordPressの一般設定、サーバー構成、DB全体は含みません。JSONを保管する場所も公開領域外を選びます。

## ZIP更新

1. WordPress全体（DB・wp-content・wp-config.php・.htaccess）をバックアップし、現行テーマZIPと設定JSONを保管。
2. 保護されたステージングで更新ZIPのSHA256を確認。
3. 「外観→テーマ→新しいテーマ→アップロード」から同じ `shikipress/` フォルダーを持つZIPをアップロードし、既存版の置換を選ぶ。
4. 公開記事数、既存URL、カテゴリー対応、設定、メニュー、予約投稿、広告テスト、SEOを確認。サーバーキャッシュを更新。
5. 合格後、本番への変更を確認し、同じZIPを導入。コードをテーマエディターで直接変更している場合は差分を先に保管。

本納品に独自更新サーバーは含みません。外部から自動更新できるとは表示しません。Node.js/Docker/ビルドは本番で不要です。

## 復旧

テーマのPHPエラーで管理画面に入れない場合、SFTP/ファイルマネージャーで該当フォルダーを退避し、以前の正常な `shikipress/` を戻します。必要ならWordPress標準テーマへ切り替えて復旧。テーマファイルだけ戻したあと設定の構造が合わない場合は同時点の設定JSON、DB変更を伴う場合は全体バックアップの対応する組へ戻します。

復旧後に投稿URL、公開範囲、予約公開、広告の未承認状態、キャッシュ、秘密情報の露出がないことを確認。テーマ設定の復元だけで記事削除や画像破損が直るとは扱いません。

## 実ファイルの差し戻し試験で確認した代替手順

1.0.1追加監査では、使い捨て検証環境へ実在する旧1.0.0 ZIPを導入した後、同じ有効テーマslugのまま1.0.1 ZIPの実ファイルへ差し替え、版検出・キャッシュ更新・設定/カテゴリーID/20記事のURL維持を確認しました。旧版からの新規DBスキーマ変更はありません。併せてstyle.cssにテスト版番号と欠陥マーカーを付け、実際の1.0.1納品ZIPへ戻すリハーサルも実施。42ファイルがZIPと一致しました。証拠はaudit-report-1.0.1.mdとtests/results/package-*.json。将来の未知のDBスキーマから戻せるという検証ではありません。

今回の環境では `wp theme install --force` が成功を表示しても、変更したstyle.cssが残る例を検出しました。ファイルシステムまたは更新処理との関係が考えられますが原因は確定していません。成功表示だけを復旧完了とせず、実ファイルを確認してください。

実際に合格した代替経路は、標準テーマへ一時切替→現在の `shikipress/` フォルダーを**公開領域の外へ退避**→納品ZIPを新規導入→ShikiPressを有効化、です。WordPressの「テーマ削除」でデータ整理をする方法ではなく、フォルダーだけを退避します。wp-config.php/DB/画像は変更せず、記事URL・設定・四季カテゴリーの対応が保たれ、変更マーカーが消え、全テーマファイルのバイトがZIPと一致することを確認しました。

本番でも最初に全体バックアップを取り、退避先と対象フォルダーを明示して実施します。正常化を確認するまで退避物を削除しません。サーバーのキャッシュ/OPcacheが残る場合は利用環境の正式手順で更新し、HTTP表示とファイル版を照合してください。DB変更があった実更新を戻す場合は、その更新に対応するDBバックアップも別途必要です。

## 任意プラグインがある場合

1.0.1はYoast SEO/WP Super Cacheへのキャッシュ無効化通知を追加します。サーバー/CDNのキャッシュは別途削除し、更新後に公開HTMLとXMLの実応答を確認してください。Contact Form 7の送信先・メール配信・迷惑送信対策設定はテーマZIPの更新だけで完成しません。最初は送信なしで表示を確認し、実メールは運営者の許可後に到達/失敗を確認します。

## CAPTCHA連携を含む1.0.2への更新

1.0.1からの更新ではテーマのファイルだけを更新し、CAPTCHAプラグインのキー・免除・保護対象を変更しません。診断画面の注意を確認し、キャッシュを削除して、実ドメインで認証成功/拒否/期限切れ/再送を確認してください。詳細はdocs/captcha-guide.md、実ZIPを使った移行試験はaudit-report-1.0.2.mdを参照。CAPTCHAプラグインを停止することは保護の停止になり得るため、公開フォームを維持したまま停止して復旧確認しないでください。

1.0.2の使い捨て検証では、フォルダー退避・不在確認後にWP-CLIが「対象が既存」として終了コード1になりました。エラー後の44ファイルは正しいZIPと一致していましたが、更新コマンドの成功とは扱っていません。検証環境では、検証済みZIPの明示展開という別経路で復旧と旧1.0.1→1.0.2移行を確認しました。本番はアップロード結果の表示だけで判断せず、実際の版・ファイル・設定・URL・公開画面を照合してください。詳細と再現用の使い捨て環境限定スクリプトはaudit-report-1.0.2.mdへ記録しています。


## 1.1.0以降の管理画面更新

[管理画面でのテーマ更新](theme-updates.md)を参照してください。1.0.4以前からは初回だけ正式ReleaseのZIPで置き換えます。以後もバックアップとステージング確認は必要です。親テーマへ直接加えた変更は更新で上書きされるため、子テーマへ分離してください。
